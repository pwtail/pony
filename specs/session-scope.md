# Цель

Зафиксировать модель сессий форка. Глобальный `db_session` остаётся прежним —
одна транзакция, которая может обнимать несколько `Database`. Объект `Database`
дополнительно даёт **точку входа в сессию**: `with db:` / `async with db:` и
`db.session(...)`. Скоуп выдаёт **разрешение** работать с базой; вложенные
скоупы и глобальный `db_session` разрешения складывают.

# Решения

1. **`db_session` — глобальный, без изменений.** `with db_session:` /
   `async with db_session:` открывает транзакцию на все базы, к которым обращаются
   внутри блока (координация primary/остальные кэши, `PartialCommitException` /
   `CommitException` — как сейчас).
2. **`Database` — точка входа в сессию.** `with db:` ≡ `with db.session():`,
   `async with db:` ≡ `async with db.session():`; `db.session(*args, **kw)`
   принимает те же флаги, что `db_session(*args, **kw)`. Скоуп выдаёт разрешение
   на свою базу; границей транзакции он не является — коммит/откат происходит
   на выходе из внешнего скоупа (решение 5).
3. **Разрешения: per-db скоуп — на свою базу, `db_session` — на все.**
   `with db:` разрешает обращения к `db`; глобальный `db_session` — к любой базе.
   Обращение к базе без разрешения внутри сессии — `TransactionError` с
   подсказкой открыть её скоуп или глобальный `db_session`. Разрешения
   **складываются** (union) и действуют до конца внешнего скоупа: выданное
   вложенным скоупом разрешение сохраняется и после его выхода.
4. **Вложенность любых скоупов разрешена.** per-db в per-db (та же или другая
   база), per-db в глобальном, глобальный в per-db — можно; запретов на
   вложенность нет. Каждый скоуп только добавляет разрешение: глобальный
   `db_session` внутри per-db расширяет доступ до всех баз.
5. **Граница транзакции — внешний скоуп.** Внутренние скоупы сами не коммитят;
   на выходе внешнего — flush + commit (при исключении — rollback) и release по
   всем кэшам, открытым внутри, включая другие базы. Отдельной per-db логики
   commit нет.

# Механизм

- В `local` (ContextLocal) хранятся разрешения сессии: `allowed_dbs` — множество
  баз, получивших разрешение, и `allow_all` — признак глобального `db_session`;
  `db_context_counter` — глубина скоупов, как раньше. Разрешения сбрасываются в
  конце внешнего скоупа.
- Скоуп — тот же `DBSessionContextManager` с параметром `database`
  (`None` — глобальный `db_session`):
  - вход — `_enter()` (проверки ddl/serializable, инкремент
    `db_context_counter`), затем выдача разрешения: `allowed_dbs.add(db)` или
    `allow_all = True`;
  - выход — декремент `db_context_counter`; commit/rollback/release — существующий
    путь `db_session` (`_commit_or_rollback` / `_async_commit_or_rollback`) на
    выходе из внешнего скоупа (где `db_context_counter == 0`), затем сброс
    разрешений.
- Guard в `Database._get_cache()`: внутри сессии (`db_context_counter > 0`) доступ
  разрешён, если `allow_all` или база есть в `allowed_dbs`; иначе —
  `TransactionError`. Существующий кэш возвращается раньше guard'а: под
  накопленными разрешениями кэш может быть только у разрешённой базы.
- Генераторная обёртка (`_wrap_coroutine_or_generator_function`) выдаёт разрешение
  на каждом возобновлении и сбрасывает его при приостановке — вместе с
  сохранением `db2cache`.

# Инварианты

- **I1.** Внутри сессии доступны только базы с разрешением: своя база per-db
  скоупов (накопленные) или все — при глобальном `db_session`. База без
  разрешения — `TransactionError`.
- **I2.** `db_session` поведенчески не меняется: мультибазовые транзакции,
  `PartialCommitException`, порядок commit — как до изменения.
- **I3.** Флаги (`retry / immediate / serializable / optimistic / ddl / strict /
  allowed_exceptions / retry_exceptions / sql_debug / show_values`) сохраняют смысл
  в обоих скоупах; `retry` по-прежнему нельзя использовать как context manager.
- **I4.** Sync/async-симметрия: `with db:` и `async with db:` проходят одни и те же
  проверки; запрет смешения режимов действует в обе стороны (sync внутри
  async-сессии и async внутри sync-сессии — `TransactionError` на входе) и для
  per-db скоупа.
- **I5.** Разрешения не переживают внешний скоуп: следующий скоуп начинает с
  чистого набора.

# Риски

- **R1. Глобалы `commit()`/`rollback()`/`flush()`** итерируют `_get_caches()` —
  внутри скоупа их вызов коммитит/откатывает **все** открытые базы (как в
  `db_session`). Явный per-db commit остаётся `db.commit()`.
- **R2. Декораторы и генераторы.** `@db.session` и `@db_session` на функциях/
  генераторах: per-db версия выдаёт разрешение и на выходе коммитит все кэши,
  открытые внутри; генераторная обёртка вручную сохраняет/сбрасывает `db2cache`
  и разрешения.
- **R3. Интерактивный режим** (`pony.MODE == "INTERACTIVE"`): вне сессии
  (`db_context_counter == 0`) проверка разрешений не применяется и не ломает
  неявный доступ.

# Вне области

- Семантика глобального `db_session` (мультибазовые транзакции) не меняется.
- Отдельного per-db пула/соединения не добавляется — используется тот же
  async-механизм, что у `db_session`.
