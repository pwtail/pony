# Цель

Миграция может указать, от каких миграций она зависит. Порядок применения —
**топологическая сортировка** (tie-break — лексикографический порядок имён
файлов), поэтому возможны ветки; линейная история — частный случай. У графа
должна быть **ровно одна голова**: если после веток их несколько, `plan`/`apply`
отказываются работать, а `pony migrations merge` создаёт миграцию слияния — `.txt`
с шапкой `-- depends:` и ASCII-схемой истории двух разошедшихся веток.

# Область

- PostgreSQL, sync; поверх этапа 1 (файлы `.sql`/`.py` в `migrations/`, трекинг
  в `pony_migrations`).
- Новый тип файла — **`.txt`**: миграция-слияние, при применении ничего не
  выполняет и только фиксируется в `pony_migrations`.

# Принятые решения

1. **Зависимости объявляются внутри файла, в первых строках** — единой
   директивой для всех типов миграций; отличается только префикс комментария
   языка файла:
   - `.sql` / `.txt`: `-- depends: 0001_initial.sql, 0002_other.py`
   - `.py`: `# depends: 0001_initial.sql` (в Python `--` — не комментарий,
     а синтаксическая ошибка; переменная `depends = [...]` не поддерживается
     и даёт понятную ошибку вместо тихого игнорирования).

   **Зависимости — только явные** (решение пользователя): миграция без
   директивы — корень (ни от чего не зависит). Каждая новая
   миграция должна явно указать родителя; если после ветвления или нового
   корня голов больше одной — это ошибка, требующая слияния (решение 6).

   Шапка — лидирующие пустые строки и комментарии; для `.py` допускается
   один docstring перед директивой, для `.sql`/`.txt` — `/* ... */` блоки.
   Директива, встреченная после кода/операторов, — **ошибка** (раньше она
   молча терялась и миграция становилась корнем).
2. **Ссылки — полные имена файлов** (`0001_initial.sql`) — как они хранятся
   в `pony_migrations` (решение пользователя).
3. **Неизвестная зависимость — ошибка** с понятным сообщением (кто на что
   ссылается).
4. **Цикл — ошибка** (с путём цикла).
5. **Порядок применения — топосорт**; tie-break («разрешение ничьей») —
   **лексикографический порядок полных имён файлов**: если несколько миграций
   готовы к применению одновременно (не зависят друг от друга), первой идёт та,
   чьё имя меньше посимвольно (`0004_users.sql` < `0005_orders.sql`; для имён
   `000N_...` это просто порядок по номеру). Правило стабильное: порядок
   одинаков при каждом запуске; при линейных явных зависимостях он совпадает
   с порядком по номерам.
6. **Ветки допускаются, но у графа ровно одна голова** (решение пользователя):
   если голов больше одной — `plan` и `apply` **отказываются** работать
   с ошибкой, которая перечисляет головы и подсказывает `pony migrations merge`.
   Несколько «голов» — незакрытая ветка, а не норма. Миграция с несколькими
   зависимостями — точка слияния.
7. **Миграция слияния — `.txt`** (решение пользователя): шапка
   `-- depends: <все головы>`; тело — ASCII-схема истории веток, **новые
   миграции вверху, `0001_initial.sql` внизу**; применение — no-op (только
   запись в `pony_migrations`, включая sha256).
8. **Команда `pony migrations merge [--name NAME]`** (решение пользователя):
   находит головы графа и создаёт `000N_<name>.txt` (по умолчанию
   `000N_merge.txt`, N = следующий свободный номер):
   - ровно **две** головы — рисует историю веток (см. ниже);
   - одна голова — «nothing to merge», файл не создаётся;
   - больше двух — ошибка: слияние поддерживается для двух веток (сначала
     смержить две, затем остальные).
9. **Команда `pony migrations plan`** (решение пользователя): вычисленный порядок
   с зависимостями и отметками применённых/ожидающих; те же ошибки графа
   (несколько голов, цикл, неизвестная зависимость).
10. **Python API: `db.migrations.plan()`** (решение пользователя) — тот же
    расчёт порядка/ошибки графа, для единообразия с CLI. **`--dry-run` у `apply`
    и `dry_run` в Python API удаляются** (решение пользователя) — их роль
    выполняет `plan`.
11. Трекинг (sha256, отдельная транзакция на миграцию, `--fake`) — без
    изменений; для `.txt` sha256 считается по содержимому файла.

# Как рисуется история веток (`pony migrations merge`)

Веток ровно две, поэтому раскладка — **две вертикальные колонки**. Новые
миграции — **вверху**, старые — внизу (как в истории коммитов): сверху новая
миграция слияния, под ней ветки, в самом низу — общий хвост до `0001_initial.sql`.
Пример тела `.txt`:

```
-- depends: 0003_orders.sql, 0004_users.sql
--
--      0005_merge.txt
--            │
--    ┌───────┴───────┐
--    │               │
-- 0003_orders.sql  0004_users.sql
--    │               │
--    └───────┬───────┘
--            │
--       0002_base.sql
--      0001_initial.sql
```

Правила отрисовки:

- первая строка файла — шапка `-- depends: headA, headB` (до картинки);
- сверху — имя новой миграции слияния (по центру);
- под ней — развилка в две колонки; ширина колонки — по самой длинной строке
  в обеих ветках (плюс отступ), поэтому картинка симметричная;
- порядок в колонке — топологический (tie-break лексикографический);
- короткая ветка добивается строками с `│`, чтобы точка слияния была на одной
  высоте;
- ниже — общий хвост: миграции, достижимые из обеих голов, по центру той же
  оси; в самом низу — самая старая (`0001_initial.sql`);
- если внутри ветки нетривиальный под-граф (несколько миграций «на одном
  уровне»), колонка перечисляет их в топологическом порядке — картинка
  остаётся линейной родословной ветки.

# Оценка ветки `origin/migrations_dev` (почему не берём целиком)

- Там есть `pony/orm/migrations/graph.py`: миграция объявляет
  `dependencies = [...]`, граф резолвит их в `parents`, есть проверка
  отсутствующей зависимости — идею берём, но в нашем формате это директива
  `-- depends:` / `# depends:` в шапке файла.
- Но граф **недоделан**: `make_route()` умеет только линейную цепочку
  (`assert len(parents) == 1`, в коде `# TODO LINEAR WAY ONLY IMPLEMENTED`),
  нет детекта циклов, ветвлений, слияний и команды merge, тестов графа нет.
- Остальная часть ветки — другая архитектура: миграции-`.py` с операциями,
  автогенерируемыми из diff моделей, свой слой `virtuals`/`vdbschema`, CLI
  `make/apply/sql/list/rename/squash/downgrade`; с этапом 1 (рукописный SQL
  как главный контракт, `.sql`/`.py` + `pony_migrations`) не совместима.
- Итог: берём идею и формат объявления зависимостей; граф (топосорт, циклы,
  одна голова, `.txt`-слияние с картинкой) пишем свой.
