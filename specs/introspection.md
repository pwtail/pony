# Цель

Режим интроспекции: пони сам читает схему БД (каталог PostgreSQL) и достраивает
entity-классы, так что в моделях можно оставить минимум — пару строк, которые
нельзя вычислить по схеме, — а остальное (названия колонок, типы, связи) пони
понимает из схемы БД. Целевое применение — **миграции данных** (`.py`-скрипты):
почти весь арсенал pony доступен без полного описания моделей.

# Зачем (сценарий)

- Есть существующая БД. В моделях — только невыводимое. `.py`-миграция данных
  пользуется entity-классами pony (ORM-запросы, связи, агрегаты) — колонки
  и типы при этом взяты из схемы, а не описаны руками.
- Интроспекция не восстанавливает всё, что можно объявить в моделях
  (`pony-entity-declarations`), — но для миграций данных нужна не вся
  информация; недостающее остаётся в минимальных декларациях или копируется
  в файл миграции данных.

# Принятые решения

1. **Интроспекция работает только для миграций данных** (решение пользователя):
   режим доступен в `.py`-миграциях; обычное приложение и обычные модели
   его не используют.
2. **Минимальные декларации — класс с невыводимыми атрибутами** (решение
   пользователя): в классе объявляется только то, что нельзя вычислить из
   схемы (имена `reverse`, каскады, конвертеры и т.п.); колонки, типы и связи
   пони добавляет сам. Пустой класс — тоже валиден.
3. **Класс ↔ таблица — конвенция + `_table_`** (решение пользователя): имя
   таблицы из имени класса (конвенция провайдера, как сейчас), переопределение
   через `_table_`. Для сущностей с application таблица вычисляется так же, как
   при маппинге: в PostgreSQL имя схемы добавляется из application
   (`(schema_name, table)`), в MySQL/SQLite — без квалификации (см. `pony-apps`).
4. **Класс — контракт, схема дополняет** (решение пользователя): объявленное
   сверяется со схемой (несовпадение — ошибка); всё, что есть в схеме и не
   объявлено, добавляется автоматически.
5. Диалекты — **PostgreSQL** (`pg_catalog`), **MySQL/MariaDB** (`information_schema`),
   **SQLite** (`pragma_table_info` / `pragma_index_list` / `pragma_foreign_key_list`).
   Oracle — вне (из `pony-migrations`).
6. Интроспекция — **sync** (граница async-режима, из `pony-migrations`) и
   выполняется в обычной (не ddl) сессии: каталог только читается, схема не
   меняется.
7. **API — `db.introspect(*entities)`** (решение пользователя): вызов из
   `.py`-миграции данных (`db` — свежая база без моделей приложения, см.
   `pony-migrations`; может быть опущен — см. решение 14); без имён
   достраивает объявленные классы из схемы БД и генерирует маппинг — после
   вызова работают обычные `db_session` и ORM-запросы.
   `db.introspect('Person', 'Book')` — отладочный режим: возвращает строку
   с описаниями указанных сущностей, выведенными из схемы (классы при этом
   не трогает); имена объявленных атрибутов сохраняются — связь выводится
   как `cars1 = Set('Car', reverse='owner')` (и `reverse='cars1'` на стороне
   ребёнка), а не `car_set`. Ссылка на сущность — имя объявленного класса
   (`'Person'`, application можно не указывать), `'application.Person'` (класс
   из application либо таблица по конвенции в его схеме) или сам класс
   (`application.Person`); для таблиц без объявленных классов — имя из дампа
   (`_entity_name`, регистронезависимо). Неизвестная ссылка — ошибка.
   Возвращается подкласс `str` с repr без кавычек — в консоли/ноутбуке видно
   готовый код. Дамп пассивен (классы не создаёт, маппинг не строит, флаг
   `_is_empty` не снимает), но перечисленные имена запоминаются: вход в
   `with db:` лениво создаёт их классы из схемы и строит маппинг (см.
   решение 14).
8. **FK на необъявленную таблицу**: если таблица-родитель не сопоставлена ни
   одному классу — колонка выводится как простой атрибут типа PK (без связи).
9. **m2m остаётся как раньше**: объявленные пары `Set`+`Set` строятся обычным
   путём (`table=`/конвенция), интроспекция их не дополняет.
10. **Имена UNIQUE/индексов выводятся** из каталога: `unique='имя'` /
    `index='имя'`.
11. **Составной PK должен быть объявлен явно** (`PrimaryKey(a, b, name=...)`);
    имя FK-атрибута выводится из колонки (суффикс `_id` отбрасывается,
    привязка — `column=...`); неявный авто-`id` замещается выведенным из
    схемы (serial → `auto=True`, identity → `auto='identity'`, имя — из
    каталога).
12. **Упомянутые, но не объявленные сущности создаются автоматически**:
    если атрибут ссылается на имя, которого нет среди классов (`Set('Car')`),
    и в схеме есть таблица по конвенции имени — класс создаётся и заполняется,
    доступен как `db.Car` (и через `attr.py_type`). Если таблицы нет — ошибка.
    Для ссылки из сущности с application класс создаётся в том же application,
    а таблица ищется в его схеме.
13. **Классы объявляются до `db.introspect()`**: минимальные декларации
    (хотя бы пустые классы) существуют к моменту вызова; явный вызов без
    единого объявленного класса и без запомненных дампом имён — ошибка
    с подсказкой.
14. **Ленивая интроспекция: `db.new()` и вход в `with db:`** (уточнение
    решения 7): `db.new()` возвращает новую `Database`, привязанную к той же
    БД (те же provider/args), но без сущностей и с флагом `_is_empty` — это
    то, что получает дата-миграция (`db = Database.instance().new()`).
    Ленивая интроспекция срабатывает **только на входе в per-db скоуп**
    (`with db:` / `async with db:` / `db.session(...)`): объявленные классы и
    запомненные дампом имена создаются из схемы (класс — по имени таблицы,
    с `_table_`, если конвенция не совпадает) и строится маппинг. Другие
    обращения — raw SQL, ORM, `db.<Имя>` — интроспекцию не запускают; в
    глобальном `db_session` её тоже нет. Если ни классов, ни запомненных имён
    нет (миграция только с raw SQL), на входе ничего не происходит: SQL
    работает без маппинга. Явный `db.introspect()` строит маппинг сам;
    `db.introspect('Person')` (с именами) — только строка, флаг не снимает;
    повторный явный вызов — ошибка.

# Что выводится из схемы БД

(Согласовано с разделом «Связь с интроспекцией» в `pony-entity-declarations`.)

- таблица → entity-класс (сопоставление — решение 3);
- колонка → атрибут; маппинг типов по диалекту.

  PostgreSQL:

  | Тип БД | Атрибут |
  |---|---|
  | int2/int4/int8 | `int` |
  | text/varchar/char | `str` |
  | bool | `bool` |
  | float4/float8 | `float` |
  | numeric | `Decimal` |
  | date/time/timestamp(tz) | `date`/`time`/`datetime` |
  | uuid | `UUID` |
  | json/jsonb | `Json` |
  | массив | `Array` |
  | bytea | `bytes` |
  | enum | `str` (с комментарием) |

  MySQL/MariaDB (`information_schema.columns.DATA_TYPE`):

  | Тип БД | Атрибут |
  |---|---|
  | tinyint/smallint/mediumint/int/bigint/year/bit | `int` |
  | tinyint(1) | `bool` |
  | varchar/char/text/*text/enum/set | `str` |
  | decimal/numeric | `Decimal` |
  | float/double/real | `float` |
  | date/time/datetime/timestamp | `date`/`time`/`datetime` |
  | json | `Json` |
  | *binary/*blob | `bytes` |

  SQLite (объявленный тип из `pragma_table_info`):

  | Тип БД | Атрибут |
  |---|---|
  | INTEGER/INT/BIGINT/SMALLINT/TINYINT/MEDIUMINT | `int` |
  | BOOLEAN/BOOL | `bool` |
  | TEXT/VARCHAR/CHAR/CLOB/NCHAR/NVARCHAR | `str` |
  | REAL/FLOAT/DOUBLE | `float` |
  | DECIMAL/NUMERIC | `Decimal` |
  | DATE/TIME/DATETIME/TIMESTAMP | `date`/`time`/`datetime` |
  | BLOB | `bytes` |
  | JSON | `Json` |

- NOT NULL → `Required`, иначе `Optional`;
- PK → `PrimaryKey`; serial → `auto=True`, identity → `auto='identity'`, MySQL
  `auto_increment` → `auto=True`, SQLite `INTEGER PRIMARY KEY` → `auto=True`;
- FK → `Required(...)` + обратный `Set` на стороне родителя;
- связочная таблица (два FK, PK из них, без доп. колонок) → пара `Set`;
- UNIQUE → `unique=True`; индекс → `index=True`; составные — `unique(...)` /
  `composite_index(...)`;
- SQL DEFAULT → `sql_default`.

# Что нельзя вычислить из схемы

Полный перечень того, что интроспекция не восстанавливает; это остаётся
в минимальных декларациях (решение 2) или копируется в файл миграции данных.

## Связи

- **Имена обратных атрибутов** (`reverse=`) — в схеме только FK; имя `Set`/`Required`
  на обратной стороне пони не знает (генерирует по конвенции).
- **Один-к-одному** — виртуальная сторона без собственных колонок в схеме не видна.
- **ORM-каскады** (`cascade_delete`) — в схеме есть только `ON DELETE` FK,
  а поведение ORM при удалении объекта может отличаться.
- **m2m через таблицу с дополнительными атрибутами** — в схеме это обычная таблица
  с двумя FK и доп. колонками: пони выведет entity с двумя `Required`, но не пару `Set`.
- **Группировка колонок в составной атрибут** (`columns=[...]` для связи с составным
  PK) — колонки читаются, но как их объединить в один атрибут — не выводится.
- **`interleave`** (CockroachDB) — вне этапа.

## Типы и конвертеры

- **Конвертеры python-типов**: `Json` (json/jsonb), `Array` (массивы), `Enum`,
  кастомные типы — в каталоге только SQL-тип; без декларации атрибут получит
  базовый тип (`str`/`bytes` и т.п.).
- **`auto` vs присвоенный PK** — частично: serial/identity читаются (`auto=True` /
  `auto='identity'`), но integer-PK без default может быть и присвоенным.

## Поведение и python-логика

- **python-`default`** — вычисляется приложением; в схеме только SQL DEFAULT
  (→ `sql_default`).
- **`py_check`** — проверка на Python-уровне.
- **`lazy` / `volatile` / `optimistic` / `hidden`** — runtime-опции, в схеме их нет.
- **STI-наследование и дискриминатор** — в БД это просто колонка; иерархия классов
  и `_discriminator_` не выводится.
- **Виртуальные атрибуты** (производные, методы) — не часть схемы.

## Ограничения и индексы

- **`@constraint.check`** — CHECK в БД есть, но обратная трансляция SQL-предиката
  в Python-метод неоднозначна (не делаем).
- **Предикаты частичных индексов** (`where`) — SQL-предикат из каталога не
  переводится в лямбду.
- **Порядок ключей индекса (DESC)** и выражения в ключах — не восстанавливаем.

Имена объектов схемы (констрейнтов, индексов, `fk_name`, `pk_name`) из каталога
вычислимы; для миграций данных они не обязательны, но интроспекция их выводит
(`unique='имя'`, `index='имя'`, `name=` у PK).
