# Цель

Добавить в форк pony ORM миграции двух типов:

1. **Миграции схемы** — описываются **SQL**. Пользователь может написать любой SQL
   и привести модели в соответствие с ним — это главный контракт. Pony *помогает*
   генерировать SQL по декларациям моделей, но это best effort: чем больше пони
   умеет генерировать, тем лучше; неполная генерация — не ограничение, недостающее
   пишется руками.
2. **Миграции данных** — описываются **скриптом** (Python). Чтобы писать их против
   существующей схемы, пони получает **режим интроспекции**: в описании моделей
   можно оставить всего пару строк, а остальное (названия колонок, типы, связи)
   пони понимает из схемы БД — и доступен почти весь арсенал pony.

Интроспекция не восстанавливает всю информацию, которую можно объявить в моделях,
но для миграций данных нужна не вся информация; недостающее можно скопировать
в файл миграции данных.

# Область

- Диалекты: **PostgreSQL** (psycopg3), **MySQL/MariaDB**, **SQLite**.
  Oracle — вне (не проверялся).
- Миграции и интроспекция — **sync**: выполняются CLI-утилитой вне event loop.
  Согласовано с решением асинхронного режима: schema-операции и интроспекция
  остаются синхронными (`pony-async-goal-and-requirements`).
- Существующий API (`generate_mapping`, `create_tables`, `check_tables`, `drop_*`)
  не меняется; миграции — отдельный путь, не трогающий его поведение.
  Единственное исключение — `CREATE SCHEMA IF NOT EXISTS` для схем
  applications в `create_tables()`/`generate_create_script()` (сознательное
  решение `pony-apps`, решение 4).

# Принятые решения

1. **Миграции делятся на два типа** (решение пользователя): **схема** — файлы
   `.sql`; **данные** — файлы-скрипты `.py`.
2. **SQL — главный контракт схемы** (решение пользователя): можно написать любой
   SQL; модели приводятся в соответствие с ним.
3. **Генерация SQL из деклараций моделей — best effort** (решение пользователя):
   пони генерирует то, что умеет; чем больше — тем лучше. Неполная генерация
   не ограничивает: недостающее пишется руками в SQL.
4. **Интроспекция — для миграций данных** (решение пользователя): в моделях можно
   оставить пару строк — то, что нельзя вычислить по схеме БД, — а остальное
   (названия колонок, типы, связи) пони понимает из схемы БД; доступен почти
   весь арсенал pony.
5. **Интроспекция не претендует на полноту** (решение пользователя): не всё, что
   можно объявить в моделях, выводится из схемы; для миграций данных нужна не вся
   информация; недостающее копируется в файл миграции данных.
6. **По умолчанию модели описываются руками** полным файлом, как сейчас;
   интроспекция — опциональный режим, не конкурирующий с руками (решение
   пользователя).
7. **Версионные файлы + трекинг** (решение пользователя): `0001_<имя>.sql` /
   `0001_<имя>.py`, порядок по номеру; применённые хранятся в таблице
   `pony_migrations` (name, sha256, applied_at); per-application scope добавляет
   колонку `app` (PK `(app, name)`) — см. `pony-apps`; каждая миграция — в своей
   транзакции. Явные зависимости между миграциями — этап 3.

   DDL `pony_migrations` зависит от диалекта: `applied_at` — `timestamptz
   DEFAULT now()` (PostgreSQL), `DATETIME DEFAULT CURRENT_TIMESTAMP`
   (MySQL/MariaDB) или `TEXT DEFAULT CURRENT_TIMESTAMP` (SQLite); проверка
   существования таблицы — `to_regclass` / `information_schema.tables` /
   `sqlite_master`. `applied_at` заполняется default'ом БД, а не из Python
   (так тип/значение не зависят от диалекта и tz-aware datetime).
8. **SQL-миграция применяется целиком** (postgres — одним запросом) в
   ddl-сессии: на SQLite/MySQL на время схемных изменений отключаются
   FK-проверки; откат — парный `0001_<имя>.down.sql`.

   На SQLite/MySQL скрипт режется на операторы: разделитель `;` учитывается
   только вне строковых литералов и комментариев; на SQLite куски
   дополнительно склеиваются через `sqlite3.complete_statement`, поэтому
   `CREATE TRIGGER ... BEGIN ... END` поддерживается. Тела процедур MySQL
   (DELIMITER) не поддерживаются — такие миграции пишутся под postgres
   либо разбиваются руками.

   Парный `0001_<имя>.down.sql` — заготовка под будущий откат: команды
   `down` в этапах 1–3 нет, а `.down.sql`-файлы инструментарий игнорирует
   (миграциями они не считаются).
9. **Python-миграция данных — скрипт** (решение пользователя): исполняется
   раннером через `runpy.run_path` с `__name__ == '__main__'` внутри обычного
   (не ddl) `db_session` раннера — схемные права дата-миграции не нужны,
   FK-проверки остаются включёнными, а изменения данных и запись в
   `pony_migrations` оказываются в одной транзакции.
   **Миграция получает свежую `Database`** — `db.new()`: клон той же БД без
   моделей приложения. Модели в миграции определяются интроспекцией
   (`db.introspect()`, решения 4–5; вызов не обязателен — маппинг строится
   лениво при входе в `with db:`, см. `pony-introspection`), а не текущими
   моделями приложения (которые могут быть новее состояния схемы в этой точке
   истории); соединение закрывается после миграции.
   Текущая база — `db = Database.instance().new()`: `Database.instance()` —
   последняя привязанная база (в приложении одна), `.new()` даёт свежий клон к
   той же БД без моделей (и с клонированным реестром applications);
   доступны ORM-запросы и `db.execute(...)`. Каталог миграции добавляется
   в `sys.path` на время исполнения: соседние модули импортируются —
   подпакетом (`helpers/...`); свободный `.py`-модуль в каталоге миграций
   сам считался бы миграцией.
   Откат данных (`down`) не определён — вне этапов 1–3.
10. **CLI** (решение пользователя): команда `pony`, подкоманда `migrations`
    (`pony migrations ...`) и запуск `python -m pony.migrations` (модуль
    `pony/migrations.py`). `make` без аргумента — `0001_initial.sql` из
    деклараций моделей; `make <имя>.py` — следующая по номеру дата-миграция
    (заготовка: `# зависит: <голова>`, `from pony.orm import Database, db_session`,
    `db = Database.instance().new()`,
    `if __name__ == '__main__':` + `with db_session:`); `make <имя>.sql` —
    заготовка SQL-миграции
    с `-- depends:`; `apply`; `plan`; `merge`. Application — позиционный
    аргумент перед командой (`pony migrations myapplication make`); без него
    команда идёт по всем applications (корня нет).

# Этапы реализации

1. **Начальные миграции.** Вместо `generate_mapping(create_tables=True)` —
   генерация `0001_initial.sql` в папке `migrations/<application>/` из
   деклараций моделей (best effort, решение 3). Применение миграций с
   запоминанием применённых в базе (`pony_migrations`). Возможность написать
   любой SQL (`.sql`) либо скрипт (`.py`) и применить его. Пока — без учёта
   порядка и зависимостей миграций друг от друга.

   Реализовано: `pony/orm/migrations.py`, точка входа `pony/migrations.py`
   (`python -m pony.migrations` и команда `pony migrations`), Python API
   `db.migrations.make()` / `apply()`. `make` без имени — `0001_initial.sql`
   из моделей, `make <имя>.py|.sql` — следующая по номеру миграция с шапкой
   `depends:`. `--fake` — пометить применённой. Трекинг — таблица
   `pony_migrations` (app, name, sha256, applied_at); каждая миграция — в
   своей транзакции; изменение уже применённого файла (как и его исчезновение)
   — ошибка. `.py`-миграция — модуль-скрипт (`runpy.run_path`,
   `__name__ == '__main__'`) с `db = Database.instance().new()`; сессию
   владеет раннер (внешняя `db_session` — одна транзакция на миграцию),
   `with db_session:` внутри файла — вложенная и не коммитит сама;
   откат (`down`) — не в этом этапе.
2. **Режим интроспекции** в пони (решения 4–5; только для миграций данных —
   `pony-introspection`).
3. **Граф зависимостей** (`pony-migration-graph`): зависимости в шапке файла
   (`-- depends:` / `# depends:`), топосорт с ветками; граф обязан иметь ровно
   одну голову — иначе `apply`/`plan` требуют слияния, а `pony migrations merge`
   создаёт `.txt` с ASCII-историей двух веток (новые миграции — сверху);
   команда `pony migrations plan` и `db.migrations.plan()` вместо `--dry-run`.

# Вне области (non-goals)

- async-миграции и async-интроспекция — вне (sync, см. «Область»);
- Oracle — вне (не проверялся);
- полная, гарантированная генерация SQL из моделей — вне (best effort, решения 2–3);
- runtime-интроспекция без файла (классы только в памяти) — возможно позже.
